# Design

## Context

仓库目前没有 Go 代码、数据库配置或测试。参见 `proposal.md` 了解动机；行为契约见 `specs/backend-runtime/spec.md` 与 `specs/service-health/spec.md`。本次是单个 Go 服务与本地 PostgreSQL 开发环境，不涉及现有服务迁移。

## Goals / Non-Goals

**Goals:**

- 让开发者以少量、明确的命令启动数据库和 Go 服务，并能验证服务与数据库状态。
- 保持 HTTP、配置、日志、数据库连接与生命周期边界清晰，方便后续增加业务 API。
- 在 PostgreSQL 故障期间仍提供存活状态、恢复后自动转为就绪，并在关闭开始后立即取消就绪状态。

**Non-Goals:**

- 定义租户数据模型、业务表或迁移框架。
- 设计生产环境数据库拓扑、鉴权和对外业务 API。
- 引入 Python AI 服务、Redis 或任务调度基础设施。
- 引入完整认证框架或额外安全中间件。

## Decisions

### 1. 单一 Go 模块与标准库 HTTP 入口

在仓库根建立 Go 模块 `github.com/rjgczp/devpilot`，以 `cmd/api` 为可执行入口、`internal` 放置配置与 HTTP 组件。HTTP 路由使用 `net/http`，日志使用 `log/slog` 的 JSON handler。当前只有两个健康接口，标准库足够；现在引入 Web 框架会增加约定和依赖而没有业务收益。第一版将 `http.Server` 的 `ReadHeaderTimeout`、`ReadTimeout`、`WriteTimeout` 和 `IdleTimeout` 分别固定为明确的默认值 5s、10s、10s、60s，不新增相应环境变量；未来新增长连接或流式接口时再单独评估写超时。后续增加业务路由时再评估是否需要框架。

### 2. 显式环境配置与启动校验

第一版仅从进程环境读取 `DATABASE_URL`（必填），以及 `HTTP_ADDR`、`LOG_LEVEL`、`READINESS_TIMEOUT`、`SHUTDOWN_TIMEOUT`（默认 `:8080`、`info`、`2s`、`10s`）。在监听端口前校验地址、日志级别、正数时长和数据库连接串格式；任何错误都只指出配置项，不回显输入值或底层可能包含连接串的错误。`.env.example` 只包含本地开发占位示例，不包含真实凭据；真实 `.env` 已被 Git 忽略。Go 进程不自动读取 `.env`，README 指导开发者显式导出变量。相比自动读取配置文件，这避免来源与优先级不明。

### 3. 连接池与就绪检查分离

使用 `pgx/v5/pgxpool` 管理 PostgreSQL 连接。启动时解析连接配置并建立池，不把一次成功的数据库连接作为 HTTP 启动前提；非法连接配置仍在监听前失败。`GET /healthz` 只反映 HTTP 进程是否仍能服务，不访问数据库。`GET /readyz` 每次请求先检查共享的“正在关闭”状态，再用该请求的 context 和 `READINESS_TIMEOUT` 限定 `Ping`，成功后在写出 200 前再次检查关闭状态：关闭中或 Ping 失败、超时返回 503，否则返回 200。每次重新探测而不缓存失败结果，因此数据库恢复后无需重启。响应使用固定的简短状态文本，不返回底层错误；日志只记录安全的错误类别，不记录原始 DSN、密码或可能含敏感数据的驱动错误。相比启动时强制连接，此方式在数据库故障期间仍能区分进程存活与依赖就绪。

### 4. 有界生命周期

用 `signal.NotifyContext` 接收 SIGINT 和 SIGTERM。收到信号后立即将共享状态切为“正在关闭”，确保仍可访问的 `/readyz` 返回 503；同时取消受管理后台任务的 context，使它们开始退出。现有 HTTP 请求继续使用自己的 request context，以便在预算内完成。此时确定唯一关闭截止时间 `signal time + SHUTDOWN_TIMEOUT`（默认总预算 10s）。用**独立于已取消信号 context**、但共享该绝对截止时间的 context 调用 `http.Server.Shutdown`，停止接收新连接并等待已有请求。随后关闭连接池等资源；因为连接池关闭可能等待借出的连接，必须以同一截止时间限制等待。只有 HTTP 与受管理资源都在截止时间前正常关闭，才输出成功日志并以零状态退出。

若 `Shutdown` 超时或异常，记录不含敏感信息的具体原因，并调用 `http.Server.Close()` 强制关闭剩余 HTTP 连接；连接池等资源仍需尝试关闭，但不得再增加固定清理等待时间或无限阻塞。可把不支持 context 的关闭操作放入受控 goroutine，主退出流程只等待至同一截止时间；截止时间已过则不再等待，返回非零状态。此时未完成的请求与未释放的连接不保证优雅完成，进程退出后由操作系统回收剩余进程资源。`Server.Close()` 只管理 HTTP 连接，不能强制终止任意后台任务；所有后续新增的受管理任务必须响应服务 context 取消并按时退出。README 明确这些限制。可注入数据库检查接口和 handler 以便单元测试；进程级测试分别发送 SIGINT、SIGTERM，并覆盖正常与超时路径。

### 5. 本地 PostgreSQL 由 Compose 提供

仓库根提供 Docker Compose 配置，使用 `postgres:18`、命名数据卷挂载到 `/var/lib/postgresql`、`127.0.0.1` 绑定的数据库端口及 `pg_isready` 健康检查；不得以 `0.0.0.0` 或空主机名发布端口。PostgreSQL 18 官方镜像的默认数据目录位于 `/var/lib/postgresql/18/docker`，因此卷挂载在其父目录，不使用旧版的 `/var/lib/postgresql/data` 挂载方式。Compose 通过必填 `POSTGRES_PASSWORD` 环境变量注入密码，文件中不硬编码密码；`.env.example` 只给占位示例，真实 `.env` 保持不入库。README 写明启动、停止、清理数据，以及数据库断开、恢复时两个健康端点的验收命令。本地使用主版本标签便于获取 18 的修订；后续部署必须固定到经验证的小版本标签或镜像 digest，避免部署时镜像内容无审查地变化。相较于要求开发者自行安装 PostgreSQL，Compose 能统一初始环境；本次不把 Go 服务容器化，以保持本地调试路径简单。

### 6. 分层验收

配置、日志脱敏、健康 handler 和关闭状态用单元测试验证；服务启动与信号处理用进程级测试验证；数据库断开与恢复用 Compose 环境的集成验收验证，检查同一 Go 进程中的 `/readyz` 从 200 到 503 再回到 200。超时 HTTP 参数通过配置或服务构造测试验证。这样既能快速运行 `go test ./...`，也能覆盖真实数据库状态变化。

## Risks / Trade-offs

- [本地 `postgres:18` 标签会随 18 的修订更新，且可能与未来部署镜像不同] → 本地仅验证连接；后续部署前对齐兼容目标并固定经验证的小版本或 digest。
- [就绪检查过于频繁导致数据库探测负载] → 每次检查设置短超时；后续部署时再依据探针频率评估缓存或节流。
- [默认端口与本机已有服务冲突] → 文档说明 `HTTP_ADDR` 和 Compose 端口如何覆盖。
- [日志可能意外包含连接错误中的敏感信息] → 只输出固定错误类别和安全字段，并用测试检查密码不出现在日志与 HTTP 响应中。
- [强制退出时仍有处理器或连接池资源未完成清理] → 优雅路径使用一个总截止时间关闭；超时路径强制关闭 HTTP、尝试清理并非零退出，不增加额外等待，在文档中明确不保证未完成请求成功。
- [后台任务忽略取消信号] → 所有受管理任务接收服务 context，并在测试中验证退出；`Server.Close()` 不能代替任务取消。
- [健康检查在信号与关闭监听器之间发生竞态] → 先切换关闭状态，再调用 `Shutdown`；凡是仍能到达 handler 的就绪请求均返回 503。

## Migration Plan

无既有运行服务或数据需要迁移。落地时先增加 Go 模块与服务，再添加 Compose 和文档；本地验证后即可作为后续开发基线。回退只需撤销本次新增文件；Compose 数据卷可由开发者按文档显式删除。
